# 一句话需求 → 标准 PRD

把模糊的产品需求推进成一份结构完整、可直接拿去评审的 PRD。核心纪律：**先澄清，后动笔；编不出来的事实必须标注为假设，而不是编造。**

## 工作流

### 第 1 步：理解输入
从用户的描述和当前对话中提取：
- 产品形态（App / 小程序 / Web / SaaS 模块 / 硬件配套…）
- 目标用户与业务领域
- 用户已给定的约束（时间点、依赖系统、合规）
- 这是"完整新产品"还是"现有产品的新功能"

不需要向用户复述这些，直接进入第 2 步。

### 第 2 步：澄清提问（必做，只做一轮）
用 AskUserQuestion 一次性问 3~4 个最高杠杆的问题，每个问题给 2~4 个选项、推荐项放第一位。问题从下面挑最关键的，不要凑数：

1. **目标用户 / 核心场景**——这个功能主要给谁用，解决什么时刻的什么问题
2. **范围边界**——本期必须做的最小集合是什么，明确不做什么
3. **成功度量**——上线后用什么指标判断成败
4. **关键约束**——时间点、依赖系统、合规要求

如果用户回答含糊、选了 Other 没写内容、或明确说"你定"：不要追问第二轮，选最合理的默认值继续，但把每个默认值作为【假设】写进 PRD 的"开放问题与假设"。

### 第 3 步：生成 PRD
先读 `assets/prd-template.md`，按模板结构逐节填写。写作规则：

- 全文中文。产品名/功能名用户没给就拟一个并标注【待定】。
- 用户故事用"作为…，我希望…，以便…"，每条配优先级 P0/P1/P2，P0 为本期必须。
- 流程图用 mermaid：主流程用 `flowchart TD`，涉及多方协作（用户/系统/人工）用 `sequenceDiagram`，节点文案 ≤ 15 字。
- 数据埋点写成表格：事件名 / 触发时机 / 事件属性 / 分析用途。指标分北极星指标和护栏指标。
- 验收标准用 Given / When / Then，覆盖正向流程和主要异常分支，每条可独立测试。
- 商业背景、竞品数据、行业数字等编不出来的事实一律标注【假设】，集中列在"开放问题与假设"。宁可留白，不可编造。
- 涉及金额、期限、SLA 的具体数值写"建议值"并说明推算逻辑。

### 第 4 步：交付
- PRD 写入 `PRD/PRD-<功能名拼音短横线小写>-v0.1.md`。
- 在对话里只给 5 行以内的摘要：关键假设、开放问题数量、文件位置。
- 主动提一句：如需评审，可再导出为 docx 或 pdf。
